# Notifications deployment handoff

In-app notifications use the existing **D1 `DB` binding**. No Durable Objects, companion Worker, Queues, new domain, extra secret or dashboard configuration is required.

## Cloudflare owner

From the repository root, with your existing Cloudflare credentials:

```sh
pnpm install --frozen-lockfile
pnpm db:migrate:remote
pnpm deploy
```

Apply migrations **before** deploying the updated app. The additive notification migration is `drizzle/0004_red_shocker.sql`; it creates a table and indexes without changing existing tables or activity. Use the project's normal deployment pipeline instead of `pnpm deploy` if it already deploys the app.

No historical notifications are generated by the migration. Activity starts generating notifications after the updated app is deployed. A rollback of application code can leave the additive table in place.

## Developer without Cloudflare access

Local development does not require production credentials:

```sh
pnpm db:migrate:local
pnpm dev
```

Tests use deterministic in-memory fakes. Playwright runs the built Worker with local D1/KV and applies local migrations automatically.

Stop other local app servers before running Playwright: Vite and Wrangler otherwise share the same local D1 files and can cause `SQLITE_BUSY` locks. The notification suite can be run with `pnpm test:e2e tests/e2e/notifications.test.ts --workers=1`.

## Behavior and verification

- New posts/reels notify followers; likes/comments notify the author; replies notify the exact answered comment author and, when different, the post author; follows notify the followed user.
- No self-notifications; like/follow history is deduplicated for the lifetime of the pair. Undoing activity does not erase history. Deleted content has no broken destination link.
- Opening the page leaves notifications unread; selecting an entry marks it read, and “Mark all as read” handles the rest.
- Badges refresh immediately on entry/navigation and every 30 seconds in visible signed-in app tabs. The Notifications list also refreshes while open. Hidden tabs pause and refresh on return.
- Notification delivery runs after successful activity writes using Workers `waitUntil`. Failures are logged as `Notification delivery failed` without failing the original action. This is best-effort delivery, not a durable queue; large follower fan-out is limited by Worker execution time. Live clients retain their previous data when refresh fails; the notification list offers retry.

After deployment, verify these activities with two accounts, unread badges on mobile/desktop, selecting a notification, and marking all read. Check Worker logs for delivery failures. No production deployment is performed by the coding agent.
